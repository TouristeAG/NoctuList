# Portal Google Sign-in Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Volunteers of an association on Google Workspace can open their portal space with their association Google account, linked to their roster entry by an admin or by themselves, while the personal e-mail stays the roster e-mail and the password login keeps working.

**Architecture:** The Google account stays its own Firebase Auth user; `portalGoogleAccounts/{googleUid}` points it at the volunteer's password-account uid, and the rules resolve that alias wherever the portal reads or writes. Links are created by processing `portalGoogleClaims/{googleUid}` (ADMIN_MATCH or LINK_CODE), Cloud Functions first and a NoctuList device after 2 minutes, exactly like `portalRequests`. The admin enables the option once at least one domain passes a DNS MX check pointing at Google.

**Tech Stack:** Kotlin Multiplatform (commonMain, Room, Compose Multiplatform, `java.net.HttpURLConnection`), Firestore/Storage rules, Node 22 Cloud Functions (`firebase-functions` v6, `firebase-admin` v13, esbuild), Firebase JS SDK 10.14.1 (gstatic modules), `node:test` + Firebase emulators.

**Spec:** `docs/superpowers/specs/2026-11-11-portal-google-login-design.md`

## Global Constraints

- Firebase backend only. Every new setting key goes into `InstitutionSettingsKeys.FIREBASE_ONLY_KEYS` and is never written to Sheets.
- `volunteer.id` never reaches the web, Firestore portal collections or Storage paths (wallet QR invariant).
- The roster `email` stays the personal e-mail; nothing in this feature writes to it.
- Admin link has priority: if `portalGoogleLinkedBy == "ADMIN"` the volunteer can neither link nor unlink.
- Domain filter: only Google accounts whose e-mail domain is in the verified list may use the portal. `gmail.com` and `googlemail.com` are never accepted as a domain.
- A domain is verified when one MX target of `https://dns.google/resolve?name=<domain>&type=MX` ends with `.google.com.` or `.googlemail.com.` (case-insensitive, trailing dot optional).
- Rules: increment `NOCTULIST_RULES_VERSION` in `firebase/firestore.rules` by one from the value in the file at the time of the change, keep `NOCTULIST_FIRESTORE_RULES_VERSION` in `FirestorePermissionErrors.kt` equal, and copy the file byte for byte to `shared/src/commonMain/composeResources/files/firestore.rules` (and `storage.rules` likewise if a copy exists there).
- Reason codes are UPPERCASE like the existing ones (`NO_ACCESS`, `SAVE_FAILED`…).
- Request/claim throttle: 1 minute for `GOOGLE_LINK`, `GOOGLE_UNLINK` and claims. A link code is valid 10 minutes after the `GOOGLE_LINK` request's `requestedAt`.
- UI and web copy: no em dashes, no artificial phrasing. App strings in the 7 `composeResources/values*/strings.xml`; web strings in the 5 languages of `portal-i18n.js` (fr, en, es, de, it).
- `webform/` is the source; `shared/src/commonMain/composeResources/files/webform/` is regenerated by Gradle (`syncWebFormResources`), never edited by hand. `webform/functions/lib/index.js` is rebuilt with `npm --prefix webform/functions run build` and committed.

## Deviations from the spec (decided while planning)

- The public `googleLogin` flag goes into the existing `portalBranding/default` document (already public, already published by `publishBranding`), not a new `portalPublic/config`.
- Settings are two `institutionSettings` documents in the existing `{value: string}` format: `volunteer_portal_google_enabled` (`"true"`/`"false"`) and `volunteer_portal_google_domains` (comma-separated, verified domains only). The rules read the list with `value.split(',')`. Unverified domains are only shown in the admin UI until they pass the check; they are never persisted.
- `GOOGLE_LINK` carries no `expiresAt`: expiry is computed from `requestedAt` (+10 min).
- The projection field is named `googleLinkAvailable` (spec: `googleLoginAvailable`); reason codes are UPPERCASE (spec shows lowercase examples).
- ADMIN_MATCH treats an alias whose target is no longer a volunteer with that `portalGoogleUid` as stale: it deletes it and goes on matching.

## Review Focus

1. Staff member who is also a volunteer signs in with the Google account they already use in the app: the portal must link and show their page, and their staff rights must stay exactly as before. (Task 2 rules test `staff google account linked as volunteer keeps member rights`.)
2. Admin removes a domain or turns the option off while a volunteer is signed in with Google: the next read must fail and the page must sign out with a clear message, not spin. (Task 2 rules tests; Task 8 step `permission-denied on projection signs out`.)
3. Volunteer closes the Google popup or picks the wrong account during "Associer": no half link, the `GOOGLE_LINK` request expires, and a retry after 1 minute works. (Task 5 test `expiredCodeIsRejected`, Task 8 popup-closed handling.)
4. Two roster entries with the same Google address typed by the admin: the admin UI refuses the second one; if it slips through via sync, ADMIN_MATCH answers `AMBIGUOUS` instead of picking one. (Task 5 test `ambiguousAdminMatchIsRejected`, Task 7 uniqueness check.)
5. Volunteer deleted or access revoked while a Google link exists: the alias must go away (revoke) or be treated as stale (deleted), so a later match does not answer DONE for a dead link. (Task 5 test `staleAliasIsReplaced`.)
